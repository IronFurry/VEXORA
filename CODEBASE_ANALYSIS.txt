1. EXECUTIVE SUMMARY
================================================================================
The project "SPCA" (branded internally as "VEXORA") is an enterprise-grade
salon management and customer booking SaaS platform backend. It supports
multi-tenant operations across multiple salon branches, managing salon
owners, salon managers, salon staff/technicians, customers, appointments,
live queue tracking, inventory, payments, customer reviews, promotional
coupons, and staff attendance.

Current State of Development:
- Database Layer: 100% complete and fully specified with 11 Mongoose models,
  including custom string identifier keys, geospatial 2dsphere indexing,
  compound query optimization indexes, and lifecycle timestamps.
- Seeding & Mock Data: 100% functional with an extensive 2,037-line seed script
  that populates realistic multi-salon data (3 salons in Bengaluru, owners,
  managers with granular permissions, staff schedules, categorized services,
  customer wishlist/favorites, appointments with queue status, payments,
  reviews, coupons, inventory, and staff attendance logs).
- API & Routing Layer: 10% initialized. The Express server boots and connects
  to MongoDB Atlas, providing a health check endpoint at '/', but controllers,
  routes, middlewares, services, and utilities remain empty folders.
- Frontend Layer: 0% initialized. The 'client' folder is currently empty.

4. ARCHITECTURAL OVERVIEW & DATA DESIGN PATTERN
================================================================================
1. Identifier System:
   Unlike default MongoDB setups that purely rely on BSON ObjectId ('_id'),
   VEXORA implements human-readable, domain-prefixed, unique string IDs:
   - Salon:            SAL-XXX (e.g., SAL-001)
   - Manager/Owner:    MGR-XXX (e.g., MGR-001)
   - Staff Member:     STF-XXX (e.g., STF-001)
   - Service:          SRV-XXX (e.g., SRV-001)
   - Customer:         CUST-XXX (e.g., CUST-001)
   - Appointment:      APT-XXX (e.g., APT-001)
   - Payment:          PAY-XXX (e.g., PAY-001)
   - Review:           REV-XXX (e.g., REV-001)
   - Coupon:           CPN-XXX (e.g., CPN-001)
   - Inventory Item:   INV-XXX (e.g., INV-001)
   - Attendance Log:   ATT-XXX (e.g., ATT-001)

2. Loose Coupling vs. ObjectId References:
   The models reference each other using these business string IDs rather than
   mongoose.Schema.Types.ObjectId with 'ref'.
   - Advantage: Clean cross-service portability, human readability in APIs,
     logs, invoices, URLs, and external system integrations.
   - Consideration: Requires explicit application-level integrity enforcement
     or custom Mongoose virtual populate references when building JOIN-like
     aggregations.

3. Geospatial Readiness:
   Salons utilize GeoJSON Point format `{ type: "Point", coordinates: [lng, lat] }`
   backed by MongoDB's '2dsphere' spatial index, enabling radius-based salon
   search and customer-proximity matching.

4. Hybrid Booking & Live Queue Engine:
   Appointments support traditional scheduled bookings as well as walk-in /
   live queue slots with real-time queue position tracking and dynamic wait times.

6. DATABASE RELATIONSHIPS & INDEXING STRATEGY
================================================================================

Entity Relationship Diagram (Conceptual):
-----------------------------------------

           [Salon] (SAL-XXX)
             ├── 1:N ──> [Manager] (owner / manager hierarchy)
             ├── 1:N ──> [Staff] (service providers)
             │             └── 1:N ──> [StaffAttendance]
             ├── 1:N ──> [Service] (salon menu)
             ├── 1:N ──> [Coupon] (discount codes)
             ├── 1:N ──> [Inventory] (stock tracking)
             └── 1:N ──> [Appointment] <── N:1 ── [Customer] (CUST-XXX)
                           ├── 1:1 ──> [Payment]
                           └── 1:1 ──> [Review]

Key Indexing Optimizations:
1. Geospatial Index:
   - Salon.location -> 2dsphere index for $near, $geoWithin, and $geoNear queries.
2. Uniqueness Enforcement:
   - Every entity has a unique business ID index (e.g. salonId, customerId, etc.).
   - Manager.email -> Unique index (case-insensitive via lowercase: true).
   - Customer.phone -> Unique index.
   - Coupon -> Compound unique candidate index { salonId: 1, code: 1 }.
   - StaffAttendance -> Compound unique index { staffId: 1, date: 1 }.
3. Query Acceleration:
   - Appointment -> Compound index { salonId: 1, appointmentDate: 1, status: 1 }
     for lightning-fast salon dashboard and live queue rendering.
   - Payment & Review -> Compound indexes on customerId and salonId with
     descending createdAt for fast timeline/history retrieval.

9. SECURITY & CONFIGURATION AUDIT
================================================================================
High-Priority Security Findings:
1. Sensitive Credentials in Plaintext:
   - 'atlas-credentials (1).env' and 'server/.env' are stored in the project
     directory containing active MongoDB Atlas credentials and password.
   - Neither file is protected by a '.gitignore' file.
   - RECOMMENDATION: Add a root '.gitignore' and 'server/.gitignore' ignoring
     '.env', '*.env', 'node_modules/', and invalidate/rotate exposed credentials.

2. Open CORS Configuration:
   - 'app.use(cors())' allows cross-origin requests from any domain without
     origin whitelisting. In production, configure origin filters.

3. Authentication Tokens:
   - 'bcryptjs' is installed and used for seeding, but 'jsonwebtoken' (JWT) is
     not yet listed in package.json dependencies. JWT will be required for
     stateless session authentication.

4. Input Validation:
   - While Mongoose schemas define field types and enums, HTTP payloads
     should be sanitized and validated at the route boundary using Zod or Joi.
